# Инструменты для автопроверки

Сабмитов на платформе всего 5 в день, поэтому каждую версию `solution.py` сначала
проверяем локально. Скрипты используют только стандартную библиотеку и `httpx`.
В ZIP для платформы они не попадают: туда идут только корневые `.py`.

| Скрипт | Что делает |
|---|---|
| `run_local.py` | Запускает `solution.py` так же, как платформа: чистая папка, `DATA_DIR` с `questions.csv` и `knowledge-base.zip`, лимит 20 минут. Проверяет `submission.csv`, сохраняет ответы для чтения |
| `mock_api.py` | Заменяет API организаторов: `/chat/completions`, `/embeddings`, `/rerank`. Работает без ключа, может имитировать сбои 429/5xx и задержки, считает вызовы |
| `check_submission.py` | Проверяет формат `submission.csv` по регламенту: заголовок, кавычки, все id, пустые и длинные ответы, заглушки |
| `judge.py` | Оценивает ответы относительно эталона. Есть быстрый режим без LLM и LLM-судья, повторяющий схему платформы: 2 раунда со сменой порядка, Score = 0.7·MatchRate + 0.3·WinRate |
| `build_zip.py` | Собирает `dist/submission.zip` и не даёт отправить архив с torch/transformers, незафиксированными версиями, `pip install` или ключами |

По умолчанию вопросы, эталоны и база знаний берутся из локальной папки `context/`
(она не в git). Другие пути передаются флагами `--questions`, `--golden`, `--kb`.

## Обычный цикл

```bash
source .venv/bin/activate

# 1. Один раз: ответы базового решения (стартера организаторов)
python tools/run_local.py --solution context/starter/solution.py --name baseline

# 2. Новая версия решения
python tools/run_local.py --name v1

# 3. Оценка
python tools/judge.py --team runs/v1/submission.csv --baseline runs/baseline/submission.csv --offline
python tools/judge.py --team runs/v1/submission.csv --baseline runs/baseline/submission.csv

# 4. Архив для платформы
python tools/build_zip.py
```

Без ключа шаги 1–2 запускаются с `--mock`. Ответы тогда ненастоящие, но проверяются
формат, время, число запросов к API и устойчивость к сбоям:

```bash
python tools/run_local.py --mock --fail-rate 0.2 --latency-ms 300 --name stress
```

Для LLM-судьи и настоящих прогонов нужны переменные `LLM_BASE_URL` и `LLM_API_KEY`.
Модель судьи задаёт `JUDGE_MODEL`, по умолчанию берётся `LLM_MODEL`. Ключ не записывайте
в файлы и не коммитьте его.

Результаты складываются в `runs/<имя>/`: `submission.csv`, `answers.md`, `solution.log`,
`summary.json`, `judge*.md`. Папки `runs/` и `dist/` в git не попадают.

## Как читать оценку

- **Быстрый режим (`--offline`)** — грубая оценка, удобная для сравнения версий между собой.
  Он считает, какие числа и пункты из эталона есть в ответе, совпал ли отказ
  («в базе нет»), и ищет числа, которых нет ни в базе, ни в вопросе. Такие числа —
  вероятная выдумка: на платформе она обнуляет вопрос.
- **LLM-судья** ближе к платформе, но это наш судья, а не их. Демо-вопросов всего 18,
  поэтому разница в 0,02–0,03 между версиями — это шум.
- Демо-вопросы не совпадают с проверочными. Улучшение должно быть общим (поиск,
  разбиение на фрагменты, промпт), а не подгонкой под 18 примеров.

## Пример: стартер на моке со сбоями

`run_local.py --solution context/starter/solution.py --mock --fail-rate 0.3` показал, что
при 30% сбоев стартер один ответ из 18 заменяет на «Не удалось получить ответ.»,
а реранкер пропускает в 8 случаях. В нашем решении нужны повторы с паузой
и осмысленный запасной ответ.
