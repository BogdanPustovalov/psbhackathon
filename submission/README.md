# Сабмит для автоматической проверки (LLM-судья)

Папка содержит решение для платформы хакатона: `solution.py` читает `questions.csv`
и `knowledge-base.zip` из `DATA_DIR`, обращается к моделям платформы и пишет `submission.csv`.

| Файл | Зачем | В ZIP? |
|---|---|---|
| `solution.py` | точка входа, всё решение в одном файле | да |
| `requirements.txt` | `httpx`, `numpy` с зафиксированными версиями из разрешённого списка | да |
| `build_zip.py` | собирает `dist/submission.zip` и проверяет файлы | нет |
| `mock_api.py` | локальный мок `/embeddings`, `/rerank`, `/chat/completions` для проверки без ключа | нет |

## Как собрать ZIP

```bash
python submission/build_zip.py
```

Результат — `submission/dist/submission.zip` (в корне архива `solution.py` и `requirements.txt`,
без вложенной папки). Скрипт проверяет, что код компилируется, версии зафиксированы и в файлах
нет ничего похожего на ключ.

## Как проверить локально без ключа

Терминал 1 — мок API:

```bash
python submission/mock_api.py --port 8765
```

Терминал 2 — прогон на демо-вопросах (папка `data/` с `questions.csv` и `knowledge-base.zip`):

```bash
DATA_DIR=путь/к/data LLM_BASE_URL=http://127.0.0.1:8765 LLM_API_KEY=dummy VERBOSE=1 python submission/solution.py
```

Мок не генерирует настоящие ответы: он проверяет, что весь конвейер работает, а в
`mock_requests.jsonl` видно, какой контекст уходит в LLM. Переменные мока: `MOCK_FAIL_RATE=0.3`
(случайные 429/503), `MOCK_CHAT_DELAY=10` (медленная LLM).

## Как устроено решение

1. **Чанкинг по структуре.** Договоры и регламенты режутся по пунктам (`3.4.`, `6.2.`), законы —
   по пунктам статьи и абзацам (до ~1400 символов). У каждого фрагмента шапка: название документа,
   номер договора, контрагент, дата, редакция и срок действия, раздел и пункт. Стартер брал
   только первые 1200 символов документа и терял, например, п. 3.4, 4.3, 6.3 договора А-08/2024.
2. **Гибридный поиск.** BM25 (своя реализация, стемминг обрезкой до 5 букв) + bge-m3 через
   `/embeddings` (эмбеддинги всех фрагментов считаются один раз при старте, батчами по 32) →
   RRF → 40 кандидатов → `/rerank` (Qwen3-Reranker-8B на платформе).
3. **Фильтр по метаданным до реранкера.** Номер договора или контрагент в вопросе (или в истории
   диалога) → чужие договоры исключаются, нужный договор и доп. соглашения к нему добавляются
   целиком. «Альфа-Трейд» и «Альфа-Трейдинг» различаются (побеждает самое длинное совпадение).
   Просто «Альфа» → в контекст идут оба договора с пометкой «уточните контрагента».
4. **Редакции.** Регламент 2023 и 2025 попадают в контекст вместе, с датами действия.
   Дата события из вопроса («в августе 2024», `12.05.2025`) сравнивается с датами действия, и
   LLM получает служебную пометку, какая редакция применима. Без даты применяется действующая.
5. **Контекст.** Документы компании маленькие, поэтому найденный документ отдаётся целиком,
   а из законов — только отобранные фрагменты. Лимит — 26 000 символов.
6. **Генерация.** Системный промпт: прямой ответ первой фразой, ссылки на пункт и документ,
   исправление ошибочной предпосылки, явное «в базе нет», без знаний модели, без помощи в
   нарушении закона, без выхода из роли, до 150 слов. Три примера стиля взяты из `demo_output.csv`.
7. **Самопроверка.** Второй вызов LLM сверяет каждое число, срок и номер пункта с фрагментами
   и исправляет неподтверждённое. Включается, только если прогноз времени позволяет.
8. **Защита от инъекций.** Строки базы знаний с командами для ИИ («игнорируй…», «для
   ИИ-ассистента…») вырезаются при загрузке. Такая строка есть в служебной записке об архиве.
9. **Надёжность.** До 4 повторов с экспоненциальной паузой на 429, 5xx и таймаут (учитывается
   `Retry-After`). Параллельность — `MAX_WORKERS`. Бюджет времени — 1080 с (`TIME_BUDGET`):
   полный `submission.csv` пишется сразу при старте (запасные ответы из базы) и обновляется
   каждые 30 с. Если эмбеддер, реранкер или LLM недоступны, решение откатывается на BM25, на
   порядок RRF или на ответ из найденного фрагмента. Пустых ответов не бывает.

### Переменные окружения

Читаются те же, что у стартера: `DATA_DIR`, `LLM_BASE_URL`/`OPENAI_BASE_URL`,
`LLM_API_KEY`/`OPENAI_API_KEY`, `LLM_MODEL`/`GEN_MODEL`/`OPENAI_MODEL`, `EMB_MODEL`,
`RERANKER_MODEL`, `TEMPERATURE`, `MAX_TOKENS` (не меньше 1024), `MAX_WORKERS`.
Дополнительно (необязательно): `TIME_BUDGET` (с), `SELF_CHECK=0` (выключить самопроверку),
`THRESHOLD_NO_ANSWER`, `THRESHOLD_CONFIDENT` (пороги реранкера в log-odds), `VERBOSE=1`.

### Пороги реранкера

Пороги 1.8 / 6.1 откалиброваны на Qwen3-Reranker-0.6B (отчёт о реранкере). Для 8B через API
шкала может отличаться. Поэтому зона влияет только мягко: при неуверенности в контекст
добавляются лучшие фрагменты BM25 и эмбеддингов, а пометка «релевантность низкая» не ставится,
если договор назван явно. В конце прогона в stderr печатается сводка оценок
(`rerank best log-odds: min/p25/median/max; zones=…`). По логам первого сабмита пороги
можно перекалибровать через переменные окружения.

## Сверка с демо-вопросами

Настоящего ключа к моделям платформы локально нет, поэтому ответы LLM сравнить с эталоном
не получилось. Проверено другое: что в промпт LLM попадает пункт, на котором построен эталонный
ответ, и нужные служебные пометки. Прогон на моке с примитивными эмбеддингами и реранкером:
**18 из 18**. Решение также прогнано через инструменты ветки `eval-tools`: `tools/run_local.py --mock`
(формат в порядке; при `--fail-rate 0.3` все 28 сбоев отработаны повторами) и `tools/build_zip.py`.
